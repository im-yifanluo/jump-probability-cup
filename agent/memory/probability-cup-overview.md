Yifan is competing in the Jump Trading Probability Cup on SportsPredict.com (2026 World Cup, 2026-06-11 → 2026-07-19). Goal: win by maximizing Relative Brier Points, RBP = (crowd_brier − user_brier) × 100 — beat the crowd average, not just be accurate. Brier = (p − o)², lower better. Stage weights: group 1×, knockout 2×, final 3×. ~72 matches × ~10 binary markets; submit integer 1–99 per market before kickoff; PATCH allowed until close, last value scores.

API: https://api.sportspredict.com/api/v1, Bearer sp_live_ key (generated manually in SportsPredict app: Probability Cup event → Profile & History → My Bots; max 2 bots/account, key shown once). 60 req/min; batch endpoint takes ≤50 predictions. Docs PDF: docs/API-Documentation.pdf.

COMPLETE REST SURFACE (verified against the full 29-page docs PDF, 2026-06-15): GET /events, GET /lobbies, POST /lobbies/{id}/join, GET /matches, GET /markets, POST /predictions, POST /predictions/batch, PATCH /predictions/{id}, GET /predictions, GET /results, POST/GET /keys, PATCH /keys/{id}. **There is NO leaderboard / standings / crowd-brier / RBP endpoint.** /results returns only OUR brier_score per settled market. Docs state explicitly (pages 12, 25): "Aggregate RBP / Smart Rating are surfaced by the leaderboard service on the SportsPredict frontend rather than this endpoint — compute your own cumulative metrics client-side." (UPDATE 2026-10-31: after the tournament, GET /results returns per-market `crowd_value` and stage-weighted `rbp`; see [[portfolio-restructure]].) So crowd_brier is NOT obtainable via API at all (not per-market, not aggregate); RBP/rank can only be seen on the website. To self-evaluate we compute Brier from /results client-side and compare to the 0.25 coin-flip + our own running average. Leaderboard caches ~1h, refreshes on Closed/Settled transition, counts only settled markets. No webhooks (poll /results). Also confirmed: /matches and /markets return only OPEN/future items — settled markets drop out, so map settled markets to fixtures via the cached snapshot.json (if still open at fetch time) or by parsing team names from the question. Quirk persists: docs say /results probability_submitted is a 0–1 decimal but live returns the 1–99 integer — handle both (v/100 if v>1).

Project architecture (settled 2026-06-11, user-approved): two layers — src/sp_api.py is the 1:1 REST transport (auth, backoff, batching); src/probability_cup.py is the domain layer (ProbabilityCup class; renamed from "Cup" at user's request — they care about clear naming and clean, maintainable code) that all analysis/model code imports: snapshot caching to data/snapshot.json, markets_df()/matches_df()/predictions_df()/results_df() as pandas DataFrames, and upsert-style submit() (POSTs new, PATCHes existing, skips past-kickoff, dry_run mode). Models work in 0–1 probability floats; only cup.py converts to the API's 1–99 ints. scripts/submit.py is the CLI to submit a predictions CSV (market_id, probability). Also: scripts/initialize.py, notebooks/01_onboarding.ipynb (executed against live API), .venv with jupyterlab+pandas+requests.

Live-system findings (2026-06-11): /events returns type as a UUID (docs say "probability") — match event by title. Lobby already joined. 71 matches / 710 open markets snapshot in data/snapshot.json. Markets are far richer than match-winner: player props (e.g. "Will Son Heung-min score?"), corners, cards, offsides, shots on target, halftime splits, AND/OR combos — ~455 distinct templates. Match names use short codes (KOR vs CZE) but questions use full team/player names. CRITICAL timing quirk (user-verified): opening_time is the actual kickoff = prediction deadline; closing_time is opening+2.5h ≈ match end — the docs PDF wrongly says closing_time = kickoff. First kickoff: KOR vs CZE 2026-06-12T02:00Z (9pm Jun 11 Chicago). User is in Chicago time (CDT). Rate limit 60/min is enforced (429s during full snapshot; client backs off).
